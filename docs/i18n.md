# Strings a reader can see

Every one of them lives in two files and nowhere else:

```
src/main/resources/messages.properties      English
src/main/resources/messages_ar.properties   Arabic
```

312 keys as of this writing. Translating the site is filling in the second file; nothing
else should need reading.

## Adding one

Put it in both files under the namespace that matches where it appears, then read it
through one of three doors depending on who renders it.

| Rendered by | How to read it |
|---|---|
| A Thymeleaf template | `th:text="#{chapter.next}"` |
| Browser code | `t('js.signOut', 'Sign Out')` — the English stays at the call site as the fallback |
| Anything on the server | `uiMessages.say("api.auth.emailTaken")` |

`UiMessages.say` resolves in the language of the request being served. For mail, use
`UiMessages.in(locale, key)` with the account's own language instead — see below.

Namespaces in use: `js`, `privacy`, `api`, `home`, `card`, `footer`, `sidecar`, `seo`,
`chapter`, `filter`, `nav`, `books`, `hadith`, `book`, `search`, `collection`, `email`,
`feedback`, `updates`, `lang`, `site`, `common`, `match`, `crumb`, `announcement`,
`browse`.

## Which language

Two different questions, and conflating them is the mistake worth naming.

**A message follows the click.** What the reader is looking at right now is the language
of the request, which comes from the URL: the Arabic site is everything under `/ar`, and
`PageLocale.of(request)` reads it. API calls are the exception — a page at
`/ar/books/al-kafi` posts to `/v1/…`, not `/ar/v1/…` — so `apiLocaleFilter` takes the
language from the referring page. That is a hint, not an identity: only a same-origin
referrer counts, and a reader whose browser withholds it gets English.

**Mail follows the reader.** It is sent from a signed-out reset form or a background job,
neither of which knows what page anyone was last on, so it goes by the preference stored
on the account (`UserAccount.locale`). That is seeded from wherever the person signed up
and changed from the language toggle. Accounts predating it hold no tag, which reads as
English — the language they have been receiving all along.

## What stops it drifting

`MessageCatalogueTest` fails the build on any of:

- a key in one bundle and not the other;
- an Arabic value left blank, or left as the English text (a value made only of
  placeholders and punctuation is exempt — it has no words to translate — and the two
  language-toggle labels are listed explicitly, since each names its language in that
  language on purpose);
- browser code asking for a key the catalogue does not have — which is silent at runtime,
  because `t()` falls back to the English beside it;
- an API response with its message written into the Java.

That last one exists because the failure is invisible from the English site. Three sweeps
of this codebase found English hardcoded in templates, sitting inside JavaScript string
literals where Thymeleaf never looks, and returned from the API — each of which rendered
correctly in English and was only visible to someone reading the Arabic page.

## What is deliberately not translated

Names of controls in other products' English interfaces — "Add custom connector",
"Developer mode" on the updates page. A reader follows those steps against an English
screen, so translating them makes the instructions harder to follow.
